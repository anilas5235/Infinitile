0 · Why this spec exists

On 2026-11-17, the day v1.0.0 was released, the owner moved the project back to its focus:

ok we need to get back into focus, all todos/ideas that do not have to do with terrain-first worldgen (and realted) or engine core. push into a new spec for later: divide between game ready mechanics, polisch,... — owner, 2026-11-17

This spec holds those items. The owner's picks for the move, the same day:

  • Persistence moves completely (Move all): the whole save concept (D2, P1–P4) is here, §3.
  • Leaf rendering is split: the flat look, the clipping and the transparency check stay in the focus; only the wind sway moves here (GAME-34).
  • Form: HTML in the style of WorldGenSpec, with its own ID prefix.

Top goal: modding. The owner made modding the high-priority goal of this spec (I want add modding capability to the new spec as a high prio goal, 2026-11-17). It is section M, right after the overview, and is scheduled first when later work starts.

What stays in focus and is not in this spec is listed in §9.

How to use this spec

  • Status. Every item has status LATER: not scheduled, no phase, no branch. Modding items are marked LATER · HIGH PRIORITY: still not scheduled, but first in line. An item moves out of this state only when the owner schedules it. It then gets a phase section here (or in WorldGenSpec, for engine-side parts), and its entry keeps the original text and gains a Done list, as WorldGenSpec §16 does.
  • IDs. Items carry GAME-nn, grouped by tens per section; modding items carry GAME-MOD-nn (section M, which has a letter so the other section numbers stay stable). Groups: GAME-MOD-01… modding, GAME-01… mechanics, GAME-10… persistence, GAME-20… content, GAME-30… feel, GAME-40… UI, GAME-50… audio, GAME-60… input). IDs are stable; a new item takes the next free number of its group. Reference them in commit messages and PR descriptions only. WorldGenSpec rule R8 holds here too: no spec IDs, dates or history in code or anything the Editor shows.
  • Fields of an item. What: a short description. Origin: the owner's words and the date. Depends on: other items or WorldGenSpec IDs. Open picks: design questions that go to the owner as options, recommendation first, before any code. Cost: a note against the frame-time goal where it matters.
  • Frame-time goal. WorldGenSpec PERF-13 (DEC-104): 120 fps or more at p95, frame time ≤ 8.33 ms, no stutters the player notices. The scheduler's main-thread budget is 2 ms per frame (PERF-17); no managed allocations per frame in steady state (PERF-04). A feature that adds main-thread work per frame brings its own measurement and keeps the goal run at its numbers.
  • UI rule. No permanent how-to text in menus or panels (like Esc: resume or Drag blocks here). The key hint row is the exception. This holds for every UI item here.
  • Assets. Every outside asset (sound, music, font, texture) needs a source and a licence check before it ships, recorded like the Kenney set and the Lilita One font (OFL).

M · Modding (high priority)

M.2 Levels

Suggested order: GAME-MOD-02 and 01 together (a loader with data mods is the first release of modding), then 05 (example and guide), then 04 (worldgen data), then 03 (scripts).

GAME-MOD-01Data mods (content packs) LATER · HIGH PRIORITY

What
A mod is a folder of JSON and PNG files. It adds voxels (textures, shape, category, light, collision); biomes, tree species and structures follow in GAME-MOD-04. At start the game reads every enabled mod, creates the objects at run time, registers them under the mod's prefix, and adds the PNGs as layers of the texture array. No mod code runs.

Open picks

GAME-MOD-02Mod loader and mod list LATER · HIGH PRIORITY

What
Every mod has a mod.json manifest. The loader finds the mods, checks each manifest, sorts them by dependencies (then by id, so the order is stable) and loads them. The main menu gets a Mods page: list, enable / disable, version, errors. A broken mod (bad JSON, missing texture, missing dependency, name clash) is skipped and shown with its error; the game starts without it and never crashes. A change takes effect at the next start, because the registries are built once.

GAME-MOD-03Script mods and event API LATER · HIGH PRIORITY

What
Mods with behaviour. The game raises events at fixed places on the main thread: block placed, block broken, chunk generated, block tick (GAME-04), world loaded, a tick per second. Mods react through a small game API: read and set a voxel, give an item, show a message. The event API is the same whatever the script language is. Console commands are one such hook already: a mod registers its own commands in the command registry (WorldGenSpec DEC-124).
Origin
Modding goal — owner, 2026-11-17.
Depends on
GAME-MOD-02; GAME-04 for block ticks; GAME-02 for item drops.
Open picks
  • Script language: none at first, data mods only (recommended for the first modding release); Lua through MoonSharp (an interpreter in pure C#, runs on Mono and IL2CPP, can be sandboxed; recommended when scripts come); C# assemblies (fastest, full .NET, Mono only, no sandbox).
  • Sandbox: yes for any script language that ships (recommended): Lua sees only the game API, no file or OS access. C# assemblies cannot be sandboxed on Mono; they have the player's full rights, like any program the player installs.
  • How much engine to open: data + events + a small API (recommended), no access to the chunk jobs, the mesher or the scheduler. This keeps engine refactors free.
Cost
Mod handlers run on the main thread inside the frame and count against PERF-13 and PERF-17. An interpreter allocates per call, which goes against PERF-04. So: frequent events (chunk generated, block tick) are batched per frame; mod time per frame is measured and shown in F3; a mod over its share gets a warning.

GAME-MOD-04World generation through data LATER · HIGH PRIORITY

What
Mods change generation through data only: new biomes (heights, top block, flora rules), tree species parameters, flora rules, structures, and overrides of WorldGenSettings values (climate, splines). The data goes into the native config the Burst jobs read, so generation stays as fast as today. A mod cannot run its own code inside the generation jobs (Burst rule, M.1).
Origin
Modding goal — owner, 2026-11-17.
Depends on
GAME-MOD-01, GAME-MOD-02; a JSON reader for settings and biomes (only a writer exists today); the biome and flora data in WorldGenSpec (BiomeSet, TreeSpecies, FloraConfigBuilder).

M.3 Cross-links

  • Persistence (§3). world.json gets a mods list (id and version) of the mods the world was last saved with. Region records already store voxels by name and orientation, not by id (§3.4), so a different mod set or load order gives other ids and the world still loads: the name palette is the id remap table. Unknown names load as placeholder blocks and keep their name (§3.4), so removing a mod does not wipe its blocks from the save. player.json stores hotbar and backpack by name too.
  • Missing mod on world load (a pick): warn, list the missing mods and let the player open anyway (placeholders) or cancel (recommended); refuse to open; or open without a word.
  • Mods change the generator. With D2, edited chunks are saved as snapshots and stay as they are; unedited chunks regenerate with the current mod set, as after a generator tuning release (§3.7). The settingsHash in world.json should cover the mod set and versions that touch generation, so a change is seen on load. A change shows as seams at the edge of kept chunks.
  • Voxel ids are never saved and never promised to mods; mods use names. A full name is at most 29 bytes (FixedString32Bytes), so mod ids stay short.
  • Security. Data mods: the readers treat every file as hostile (size limits, no paths outside the mod folder, no crash on bad input). Script mods: sandboxed Lua, or C# with the player's full rights and a clear warning when it is enabled.
  • 120 fps. Load-time work is free against the goal; mod code per frame counts against PERF-13, PERF-17 and PERF-04 (GAME-MOD-03).
  • Determinism. Data mods keep generation inside the Burst jobs under the same rules (GEN-16, FloatMode.Strict). A managed pass would not.
  • Multiplayer is not planned, so mod sets never need to be synced between players.

Kept chunks

  • The first edit in a chunk marks it edited and every chunk within 2 chunks of it (5 × 5 = 25) kept. A kept chunk is saved whole (its interval list as runs) and from then on loaded from disk.
  • The ring keeps the surroundings of a build (garden, path, the hill behind it) intact through a terrain update; the seam to regenerated land sits 64 blocks away. A ring of 1 would already cover all tree overhang (flora padding 11).
  • Ring chunks are always loaded when the edit happens (they are within 2 chunks of the player's reach), so they come from the same generator as the edited chunk.
  • Each record stores the generator version and settings hash that built it (diagnostics, a later "Update terrain").
  • Cost: one lone block edit keeps 25 chunks ≈ 0.5 MB; a typical hour of building in one area ≈ 2.2 MB (§3.6).
  • Light is recomputed for kept chunks as for any chunk.

Region file .ivr (binary, little endian)

Header   "IVRG" | u16 format | u8 regionSide (16) | u8 compression (0 none, 1 deflate) | i32 rx | i32 rz
Table    256 × { u32 offset | u32 length | u32 crc32 | u8 kind }   kind 0 = none, 1 = snapshot edited, 2 = snapshot ring
Records  per chunk, each compressed on its own:
           u16 generatorVersion | u8[8] settingsHash prefix
           u16 paletteCount; palette: { u8 len, utf8 "package:Name", u8 orientation }
           u32 runCount;     runs:    { u16 palette index | varint length }
  • Size: a kept chunk is 15–20 k runs, 60–80 KB raw, 15–25 KB deflated. A region with a build area holds 25–110 records, ≈ 0.5–2.5 MB. The cache keeps records compressed, so a save deflates only changed chunks, then writes the whole file (≈ 10–30 ms of IO-thread time for 2 MB).
  • Palette by name + orientation per record: new, removed and re-ordered voxels or packages don't break a save (ROT-02). A record is rewritten alone, without touching other chunks' palettes.
  • Unknown name on load (voxel deleted or renamed): a visible placeholder block; the original name is kept, so the next save writes it back unchanged. A voxel-renames.json table (old → new) handles deliberate renames.
  • Write = whole region file: serialise, write r.X.Z.ivr.tmp, flush to disk, File.Replace(tmp, target, bak). Regions hold at most a few MB, so a rewrite is cheap and needs no sector allocator.
  • Compression: Deflate through System.IO.Compression (in Unity's .NET Standard 2.1, Mono and IL2CPP, no package).
  • Corruption: CRC per record. A bad record or unreadable file: the file is moved aside (r.X.Z.ivr.corrupt-<date>), the .bak is tried, else the chunks load as unedited. Never a crash.

Versions and migration

  • format integers in world.json, player.json and each region header. They are not the game's semver.
  • Older format → migration steps (1 → 2 → …) on load; the old folder is zipped to saves/_backups/ before the first migrated save. Newer format than known → the world list shows it as "needs a newer version" and does not open it.
  • Game semver (from 1.0.0): a major bump only when a save can't be migrated (matches Docs/Releases.md: major = breaking what players already have). Generator tuning is minor: kept chunks are untouched by it.

  • KeepSet + RegionCache (new, owned by VoxelWorld, outside ChunkManager): which chunks are kept, and their latest records (compressed). Because they are not part of the chunk store, unload, Regenerate and ChangeDrawDistance keep edits even before anything is written: they rebuild ChunkManager and the schedulers, and the new scheduler gets the same cache. This also ends the loss within a session (walk away and back) where nothing goes to disk (tests, goal run, Editor Play).
  • RegionCache: regions within the load distance + one region, plus every dirty one. A clean region outside that ring is dropped; a dirty one is saved first (in a session without disk it stays in memory instead).
  • Gate: the data stage dispatches only a chunk whose region is ready (read, or known absent from the directory listing taken at world open). Prefetch runs ahead of the focus, so the gate should almost never hold a chunk.
  • IO thread: one dedicated background thread, not a Unity job (file reads block, job workers must not). Palette names → ids are resolved there once per record, with a read-only dictionary built at world open.
  • Decode job (Burst): inflated runs + id table → the chunk's interval list and OccupiedPartitions. Kept chunks skip ChunkJob entirely, so the generator's hot loop is not touched (no PrepareChunkMaps risk).
  • Snapshot: copying a loaded chunk's interval list (15–20 k nodes) is a memcpy on the main thread; the conversion to runs + palette and Deflate run on the IO thread.

When to save

  • Autosave every 5 min (a setting later): only dirty regions + player.json + world.json (manifest last).
  • A region leaves the cache while dirty → saved then.
  • Quit / "Save and quit to title" → a synchronous final save (waits for the IO thread).
  • OnApplicationPause / focus loss on desktop: not needed; a crash loses at most one autosave interval.
  • Dirty tracking: a dirty bit per kept chunk (set by an edit in it; a ring chunk is dirty once, until its first snapshot) and per region; the player is written with every save.

Generator changes (Q4′)

  • Kept chunks (edited + ring 2) never change: the build and 64 blocks around it stay exactly as built.
  • Every other chunk comes from the current generator. After a tuning release a seam (a step, a cut tree, a cave ending flat, a water edge) can appear on the chunk grid 64 blocks from a build; nowhere closer.
  • world.json stamps generatorVersion + settingsHash; each record stamps the pair that built it. The world list shows "terrain updated" when the current pair differs from the one last played.
  • generatorVersion is a constant in code, bumped by hand when generator code changes output; settingsHash comes from WorldGenSettings.ToCanonicalJson. The golden-hash test (P2) fails on any output change, so a missed bump is caught.
  • Float determinism no longer matters for saved land (it is stored, not regenerated). It only decides whether regenerated land matches on both sides of a seam on another machine (§3.7).

Tests, Editor and the goal run (Q10)

  • No world session → nothing is read or written. That covers tests, the goal run (AutomatedRun.Active) and Editor Play without the menu: a throwaway world with the asset's seed, as today.
  • In all three, KeepSet and RegionCache still work in memory, so edits survive unload, Regenerate and ChangeDrawDistance within the session, and the save path can be tested without disk through an in-memory file layer.
  • Editor Play from the MainMenu scene (after P3) uses real worlds like a player build.

3.7 Generator changes and determinism

Is generation bit-identical?

Read on feature/hud-settings-menu, Burst 1.8.28, Mathematics 1.2.1, 2026-11-17.

  • Every job that runs the sampler is [BurstCompile(CompileSynchronously = true, FloatMode = FloatMode.Strict)] (GEN-16, guarded by a test in ChunkJobTerrainFirstTests). CompileSynchronously keeps the Editor from running the managed fallback while Burst compiles.
  • Noise is the project's own SeededSimplex: integer hash gradients + float add, mul, floor. No Mathf, UnityEngine.Random or System.Random in the generator. Flora spacing and placement are integer hashes.
  • Transcendental functions in shipped generation: only the cave worms (math.sin, math.cos, math.atan2 in Worms.cs). math.exp sits in ParameterSpaceWeighting, which the shipped asset does not use (both blend methods are DistanceBlend). math.sqrt (NestedSpline) is exact under IEEE.
  • No Burst AOT settings file, so players use the defaults (x64 Windows/Linux: an SSE-level and an AVX2 variant, picked at run time by CPU). The Editor JIT-compiles for its own CPU.

What that means:

  • Same machine, same build: identical (the existing determinism tests show it).
  • Windows vs Linux player on the same CPU family: very likely identical (same compiler and targets, no OS math library).
  • Different CPUs (AVX2 or not), and Editor vs player: probably identical for add, mul, floor, sqrt. Not guaranteed for the worms' sin, cos, atan2: Burst's own approximations may compile differently per target, and Burst gives no cross-platform promise (FloatMode.Deterministic is documented as reserved for future use; whether Strict rules out FMA fusing on AVX2 is not stated plainly).
  • Where a difference would show: almost nowhere on the surface (heights and thresholds round to whole blocks, so a last-bit change flips a block only at an exact boundary). Worm paths add sin/cos over many steps, so a cave wall could move by one block on another machine.
  • Burst disabled (Jobs menu or a Burst compile error): the jobs run in Mono, math.sin goes through System.Math, and caves differ for sure.
  • Not measured yet: no cross-machine or Editor-vs-player hash exists. Hence the golden-hash test (size S) in P2: hash the voxels of a fixed set of chunks (caves on, several biomes) per seed, store it, assert it in EditMode and in a development player on Windows and Linux.
  • Weight: a one-block difference matters only for deltas (an edit next to a cave wall). With snapshots the saved chunks are exact copies, so with D2 a difference can only show up as a seam. Generator changes (tuning releases) move terrain by tens of blocks and matter far more.

GAME-36Texture variants for blocks LATER

What
A block face can show one of several textures instead of always the same tile, so large areas of one block (grass, dirt, sand, stone, moss, litter, snow) do not show a repeating grid. Each block lists a few variant tiles, optionally with weights. A hash of the block's world position picks the variant (the same block always looks the same and the world stays deterministic). Two cheap forms come first, then real variants:
  • rotate or mirror the one tile per block (no new art; not for tiles with a direction, such as grass sides or logs),
  • separate variant tiles: the variants sit as neighbouring layers of the texture array, so the shader adds the picked offset to the base layer.
Variants are a look only; the voxel id does not change, so saves, the registry and the surface rules are not affected.
Origin
wirte up vareinte textures for later — owner, 2026-11-25, while the ground tiles (coarse dirt, moss, litter) were redrawn in WorldGen v2 V5 (PR #88).
Depends on
— (new tiles are drawn with Docs/Tools/make_tiles.py in the existing style).
Open picks
  • Which blocks get variants first, and how many per block (2–4).
  • Rotation/mirror only, separate tiles, or both.
  • Per face or per block (top and sides the same variant or not).
  • Together with a slight per-block brightness change, which the owner left open on 2026-11-18 (“not sure”, maybe later).
  • Data: a variant list on the voxel definition; mods can add variants to their own blocks (GAME-MOD-01).

GPU only: one hash of the block position and an add to the layer index per pixel or per face in SolidVoxel, CutoutVoxel and TransparentVoxel; no CPU or meshing cost, and faces stay as they are. The texture array grows by the extra tiles (128 × 128 each, about 85 kB with mipmaps at 32 bits). Biome tint, AO and the light must read the same block as today. The item icons keep the base tile.
