Game Spec — later work

Game features for Infinitile that wait until the owner schedules them: game mechanics, worlds and persistence, content, feedback and feel, UI and menus, audio and input. The current work is terrain-first world generation and the engine core; that lives in WorldGenSpec.html.

0 · Why this spec exists

On 2026-11-17, the day v1.0.0 was released, the owner moved the project back to its focus:

ok we need to get back into focus, all todos/ideas that do not have to do with terrain-first worldgen (and realted) or engine core. push into a new spec for later: divide between game ready mechanics, polisch,... — owner, 2026-11-17

This spec holds those items. The owner's picks for the move, the same day:

  • Persistence moves completely (Move all): the whole save concept (D2, P1–P4) is here, §3.
  • Leaf rendering is split: the flat look, the clipping and the transparency check stay in the focus; only the wind sway moves here (GAME-34).
  • Form: HTML in the style of WorldGenSpec, with its own ID prefix.

What stays in focus and is not in this spec is listed in §9.

How to use this spec

  • Status. Every item has status LATER: not scheduled, no phase, no branch. An item moves out of this state only when the owner schedules it. It then gets a phase section here (or in WorldGenSpec, for engine-side parts), and its entry keeps the original text and gains a Done list, as WorldGenSpec §16 does.
  • IDs. Items carry GAME-nn, grouped by tens per section (GAME-01… mechanics, GAME-10… persistence, GAME-20… content, GAME-30… feel, GAME-40… UI, GAME-50… audio, GAME-60… input). IDs are stable; a new item takes the next free number of its group. Reference them in commit messages and PR descriptions only. WorldGenSpec rule R8 holds here too: no spec IDs, dates or history in code or anything the Editor shows.
  • Fields of an item. What: a short description. Origin: the owner's words and the date. Depends on: other items or WorldGenSpec IDs. Open picks: design questions that go to the owner as options, recommendation first, before any code. Cost: a note against the frame-time goal where it matters.
  • Frame-time goal. WorldGenSpec PERF-13 (DEC-104): 120 fps or more at p95, frame time ≤ 8.33 ms, no stutters the player notices. The scheduler's main-thread budget is 2 ms per frame (PERF-17); no managed allocations per frame in steady state (PERF-04). A feature that adds main-thread work per frame brings its own measurement and keeps the goal run at its numbers.
  • UI rule. No permanent how-to text in menus or panels (like Esc: resume or Drag blocks here). The key hint row is the exception. This holds for every UI item here.
  • Assets. Every outside asset (sound, music, font, texture) needs a source and a licence check before it ships, recorded like the Kenney set and the Lilita One font (OFL).

2 · Game mechanics (game-ready)

The game is creative-only today: every slot holds a BlockStack with an unlimited count, breaking is instant, and nothing drops (DEC-113). These items turn it into a game with goals.

GAME-01Survival mode LATER

What
A survival game mode beside today's creative mode, chosen per world. Inventory counts become real (the inventory is already count-ready), mining takes time and drops items, maybe health and hunger. It ties together GAME-02, GAME-03, GAME-05, GAME-07 and GAME-31. A big feature: a concept session first, as for persistence, then design picks.
Origin
add to TODO list: survival mode — owner, 2026-11-17. Inventory: They will have counts, but for now only "creative" mode (DEC-113, 2026-11-17).
Depends on
GAME-02 (mining and drops), GAME-08 (count fix first), GAME-10 (the mode is stored in world.json); the Create World screen of GAME-12 shows the mode greyed until this exists.
Open picks
  • Health, hunger, fall damage, death and respawn: which, and how hard.
  • Switching mode in a running world: allowed or not.
  • Stack size per item.
  • What the HUD shows in survival (hearts, hunger bar) in the PR #70 style.
Cost
The mode itself is cheap (a few HUD values). The cost sits in its parts: item entities (GAME-02) and mobs (GAME-06).

GAME-02Mining time, item drops and pickup LATER

What
In survival, breaking a block takes time, set per block type (hardness), and the broken block drops as an item that the player picks up by walking near it. Creative keeps instant breaking without drops. The item drop and pickup system does not exist yet; GAME-07 and GAME-03 need it too.
Origin
Split out of GAME-01 for this spec. The owner's items that need it: add to TODO list: survival mode, add to TODO list: block breaking animation (survival only), add to TODO list: torch item drop when block below breaks — owner, 2026-11-17.
Depends on
GAME-01 (mode and counts).
Open picks
  • Mining time per block type, and whether tools exist (tools need GAME-03).
  • What drops: the block itself, or something else (stone → cobble, leaves → sapling, grass → dirt).
  • Drop look: a small spinning block, or the flat icon.
  • Pickup radius, merge of nearby drops, despawn time.
Cost
Item entities are the risk: a Rigidbody per drop is too expensive in large numbers. Use a pooled, simple mover (gravity plus a voxel lookup for the floor, no PhysX), cap the live count, merge drops close to each other. No allocation per drop (PERF-04). A tree felled at once must not create a stutter.

GAME-04Block tick system LATER

What
An update system for placed blocks, which does not exist yet: blocks that change over time (a plant grows a stage, later maybe fire, water flow or leaf decay). GAME-05 is the first user. It is an engine-side piece; when scheduled, its engine rules go into WorldGenSpec Part E.
Origin
From the growing-plants item (GAME-05): Needs a tick/update system for placed blocks, which doesn't exist yet — coordinator's note on the owner's item, 2026-11-17.
Depends on
—. Its changes go through the normal edit path, so the chunk is saved by GAME-11.
Open picks
  • Random ticks (a few random voxels per loaded chunk per tick) or scheduled ticks (a queue of voxels with a due time), or both.
  • Tick rate, and which chunks tick (all loaded, or only near the player).
  • Whether ticks continue while a chunk is unloaded (catch up on load by elapsed time).
Cost
At draw distance 12 there are 625 loaded chunks. The search for tickable voxels runs in a Burst job on workers; applying the changes is main-thread edit work and goes under the frame budget (PERF-17), sliced across frames. Each changed voxel rebuilds its partition's mesh and light, so many changes in one frame cost mesh-stage time; changes are batched per partition. Needs its own benchmark row (PERF-03).

Open picks

Its phases are P1 → P2 → P3 → P4, then P5.

3.1 Persistence decisions (owner, 2026-11-17)

Asked as options; binding. The question numbers are those of the concept.

#Pick
Q1′D2: every edited chunk and a ring of 2 chunks around it (5 × 5 = 25 chunks) are saved whole as "kept chunks" and loaded from disk from then on; all other land is generated. Deltas were dropped after the owner's objection above. Option C (save every visited chunk) was rejected: about 1 GB per 10 min of flying.
Q2Region files of 16 × 16 chunks (512 × 512 blocks), rewritten whole and safely (temp file, replace, .bak).
Q3Deflate (System.IO.Compression).
Q4′Unedited land follows the current generator. world.json stamps the generator version and the settings hash; the world list marks "terrain updated" (a status, not a hint).
Q5Backpack and hotbar per world, in player.json.
Q6Autosave every 5 min (changed regions only), plus when a changed region leaves memory, plus on quit.
Q7PR order P1 → P2 → P3 → P4.
Q8Create World asks name and seed (empty = random, text allowed).
Q9Delete: confirm dialog, then the folder is removed.
Q10Editor Play without the menu saves nothing: a throwaway world, like tests and the goal run (differs from the concept's first recommendation).

Saved: kept chunks (interval runs, palette by block name and orientation), seed and generator stamp, player pose and movement mode, inventory, time of day, world meta (name, created, last played, play time, mode). Not saved: light (recomputed). Game settings (draw distance, frame rate, vSync, later key bindings and volumes) stay global in PlayerPrefs. Layout: <persistentDataPath>/saves/<name-slug>-<4 hex>/ with world.json (written last, the commit point), world.json.bak, player.json, worldgen.json (reference only), session.lock, region/r.X.Z.ivr.

GAME-11P2 Block edits (D2) LATER

What
A KeepSet (edited chunks + ring 2), the region file format with snapshot records stamped with generator version and settings hash, an IO thread, a RegionCache with a gate and prefetch, a Burst decode job for kept chunks (it replaces ChunkJob for them, so ChunkJob stays untouched), snapshots on unload, autosave, region eviction and quit, a palette by name and orientation, a placeholder for unknown names, CRC and corrupt-file handling, a format version with one migration fixture, a generatorVersion constant, and a golden-hash test (the voxels of a fixed set of chunks per seed, in EditMode and in a development player on Windows and Linux). Size L.
Origin
Persistence concept P2; save game and load game and the delta objection above (owner, 2026-11-17).
Depends on
GAME-10.
Open picks
None left from the concept. Risks: snapshot copy cost on the main thread in save bursts; lifetime of the inflated buffers in the decode job; region size with many builds (about 0.5 MB per lone edit); DeflateStream on the Linux player; a missed generatorVersion bump (the golden hash catches it).
Cost
Main thread: a region check per chunk at dispatch (< 1 µs), marking chunk + ring on an edit (< 1 µs), copying one kept chunk's interval list for a save (20–60 µs), sliced by the frame budget (PERF-17). IO thread: read a region 1–5 ms, compress a chunk 1–2 ms, write a region 10–30 ms. Worker: decode a kept chunk 0.2–0.5 ms (generation is 5–7 ms). Quit waits under 1 s for typical worlds. Pins: ChunkJob bench unchanged; goal run p95 and frames over 8.33 ms unchanged on a world with a build area; a PlayMode test that an autosave of 110 changed kept chunks never puts a frame's scheduler time over the budget plus one item. Disk: about 2.2 MB per hour of building; flying writes nothing.
Tests
Edit → save → reload → same voxels in the edited chunk and the ring (with turned variants and a new voxel that shifts ids); a ring chunk is loaded from disk, not generated; edits survive unload and ChangeDrawDistance without a save; a changed settings hash keeps kept chunks and regenerates the rest; truncated or bad-CRC region; an unknown name round-trips; migration fixture; golden hash.
