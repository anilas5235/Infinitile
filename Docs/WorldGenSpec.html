World Generation Spec — Terrain-first & Biome-first

Implementation specification for the voxel engine in Assets/Engine, written for a coding agent. Part I builds the world generation; Part E holds the engine-wide rules for performance, culling and lighting. Part II records the engine cleanup and the improvement ideas that were implemented after Part I, and plans the next generation improvements (Phase G). Part III, which comes later and stays separate, builds the tooling that collects research data from it.

Unity · Burst · Jobs · C# Part I: priority 1 Part E: performance, culling, lighting Part II: cleanup & ideas done 2026-10-21; Phase G planned Part III: priority 2, separate assembly Decisions recorded 2026-10-17 (§14), 2026-10-21 (§15.4) and 2026-10-24 (§17.8)

  • Read order: §2 (rules) → §3 (what exists, known defects and review findings) → §11.7 (Unity CLI workflow) → §11.1 and §12 for Phase S → afterwards §5 (shared foundations) and the section of the current phase (§13 points to it).
  • Requirement keywords: MUST is mandatory; SHOULD is strongly recommended (deviate only with a stated reason in the commit/PR); MAY is optional.
  • Requirement IDs are stable. Part E: PERF-, CUL-, LGT-. Part I: GEN-, TRN- (Terrain-first), BIO- (Biome-first), BLD-, VEG-, INT-, TST-, TOOL-. Part III: RES-, EXP-, ANA-. In Part II, §15–16 record finished work and have no requirement IDs; §17 continues the Part I prefixes (GEN-30…, VEG-10…, TST-30…, PERF-10, INT-31). Reference IDs in commit messages and PR descriptions only. Since the cleanup (§15, R8) the code and everything the Editor shows carry no spec references.
  • Decisions taken by the user are recorded in §14 (2026-10-17), §15.4 (2026-10-21) and §17.8 (2026-10-24) and are binding. If the agent hits a new design question, it asks the user instead of choosing silently.
  • Placeholders. Numeric defaults (spline points, biome positions, biome height parameters, flora rules) are starting values so the world looks plausible. The user tunes them; the agent must not "optimise" them on its own (R5).
Part I World generation — priority 1

1 · Purpose & scope

Build a world generator that supports two architectures and four biome-blending methods, selectable by configuration, with deterministic vegetation. Concretely:

  1. Terrain-first: height from noise fields via splines; biome chosen afterwards (6D, including height); the biome never changes height (§7).
  2. Biome-first: biome chosen first (5D); height computed from the biome's own height parameters (§8).
  3. Both share the same five noise fields and the same height formula (§5).
  4. Four blending methods applied in two stages: a material stage (surface blocks and flora, both architectures) and a height stage (Biome-first only) (§9).
  5. Six biomes: Plains, Desert, Mountain, Snow, Forest, Ocean (§6).
  6. Deterministic, seamless vegetation driven by the material-stage weights (§10).
  7. Editor preview tooling to look at and compare configurations (§11.4).

Every combination must be playable in game: 2 architectures × 4 methods = 8 configurations.

Non-goals for Part I

  • No data export, experiment runner, metrics or analysis. That is Part III and lives outside the engine (§18).
  • No 3D density fields, overhangs or caves. The world is heightmap-based (2.5D): exactly one surface height per column.
  • No changes to meshing, rendering, colliders or the scheduler beyond what integration needs — except the Phase S fixes and Part E (culling, lighting). Performance is a goal throughout (§E1).
  • Ores, caves and structures (currently commented out in ChunkJob) stay disabled.

2 · Agent ground rules

R1MUSTFollow Assets/Engine/Docs/SystemOverview.md: keep responsibilities in their layers, hook into existing events, make minimal changes, check disposal of every native container you create.
R2MUSTKeep all per-column generation code Burst-compatible: no managed types, no virtual dispatch, no allocations inside hot loops. Select architecture and method with enum switches, not interfaces.
R3MUSTEvery generated per-column quantity is a pure function of (worldX, worldZ, seed, config) (§5.1). Never derive randomness or neighbourhoods from the chunk origin or chunk-local indices.
R4MUSTWorld generation must not contain research code: no exporters, metric code, experiment plans or file output for analysis. It offers a clean public sampling API (GEN-17); everything research-related is built on top of it in Part III.
R5MUST NOTsilently tune design parameters (spline points, biome positions, biome height parameters, flora rules). Provide tooling, previews and calibration suggestions; the user sets the values.
R6SHOULDWhere code follows a known source, say so in a short comment (e.g. // PV formula after Minecraft Wiki, "World generation"). Where something is an own extension (e.g. the jaggedness spline), say that too. Never invent sources.
R7SHOULDUpdate Docs/WorldGenerationPipeline.md at the end of each phase in the existing style (mermaid flowchart + description), and fix doc paths that no longer match (§3.3).
R8MUST NOTput spec references into code or anything the Unity Editor shows: no § sections, requirement, decision or review IDs, phase names, dates or project history in comments, tooltips, headers, labels, HelpBoxes, log, warning, exception or assert messages, #region names, shader comments or asset notes. Comments state purpose, units, invariants and the non-obvious why. Spec IDs belong in commit messages, PR descriptions and this document (established by the 2026-10-21 cleanup, §15).

5 · Shared foundations

Everything here is used identically by both architectures.

5.1 Pure sampler and public API

GEN-01MUSTImplement a static, Burst-compiled sampler (WorldSampler) with one entry point per quantity, all taking world coordinates and a read-only config: SampleFields(x,z), SampleColumn(x,z) → ColumnSample (fields, height, material weights, height weights, surface source biome, flora decision). The chunk job and the preview window both call it.
GEN-02MUSTCaching (e.g. a padded per-chunk lattice for spatial methods, §9.3) is allowed only if the cached result is bit-identical to the uncached pure function (TST-01).
GEN-03MUSTNeighbourhood lookups use a world-aligned lattice (points at integer multiples of the stride), never chunk-relative offsets.
GEN-17MUSTExpose a public region API in the engine assembly, used by the preview and later by Part III: WorldGenApi.SampleRegion(in WorldGenRequest req, ref RegionBuffers outBuffers) → JobHandle. WorldGenRequest = settings snapshot, seed, origin, size; RegionBuffers = caller-allocated NativeArrays for any subset of: height (float), column height (int), biome hard class, dominant material biome, material weights, height weights, surface source biome, flora species, flora source biome, fields T F C E W PV. Unrequested buffers are left unallocated and skipped. Also expose WorldGenSettings.ToCanonicalJson() (INT-02). This API is generic world-gen functionality, not research code.

5.2 Hashing

GEN-04MUSTProvide Hash32(int x, int z, uint seed, uint salt) with good avalanche behaviour and Hash01(...) → float in [0,1) from the top 24 bits. Every random decision has its own salt constant (surface pick, flora biome, flora species, tree priority, noise gradients, …), declared in one file HashSalts.cs.
// sketch – any well-tested 32-bit integer mix is fine
static uint Mix(uint h){ h ^= h >> 16; h *= 0x7feb352d; h ^= h >> 15; h *= 0x846ca68b; h ^= h >> 16; return h; }
static uint Hash32(int x, int z, uint seed, uint salt){
    uint h = Mix((uint)x * 0x9E3779B1u ^ salt);
    h = Mix(h ^ (uint)z * 0x85EBCA77u);
    return Mix(h ^ seed);
}
static float Hash01(int x, int z, uint seed, uint salt) => (Hash32(x, z, seed, salt) >> 8) * (1f / 16777216f);

5.3 Seeds and field offsets

GEN-05MUSTEach noise instance (T, F, C, E, W, each detail octave Ni, P, warp field) gets its own seed-derived salt for its gradients (GEN-15) and, where the existing NoiseProfile/WarpedNoiseLayer code is kept, an offset o with |o| ≤ 104 from Hash01. This replaces the seed-added-to-position code (D-03) and the hand-picked decorrelation offsets in NoiseCalculator.
GEN-06SHOULDDocument that float32 precision degrades beyond |x|, |z| ≈ 105–106; no special handling required for play.

5.4 Noise basis

GEN-15MUSTImplement an own seeded 2D simplex noise whose lattice gradients come from Hash32(i, j, seed, salt) — no permutation table, therefore no period (Unity's cnoise/snoise use a mod-289 permutation and tile). Use it for all fields, octaves, P and the warp field. Keep NoiseProfile (fBm) and WarpedNoiseLayer as wrappers, switched to the new basis.
GEN-16MUSTDeterminism: every job that calls the sampler is [BurstCompile(CompileSynchronously = true, FloatMode = FloatMode.Strict)]. The preview and chunk generation call the sampler only from inside such jobs, never from managed main-thread code, so a Mono fallback during async Burst compilation cannot change results.

5.6 Detail octaves and peak noise

GEN-09MUSTProvide K detail octaves (default K = 6, wavelengths 512, 256, 128, 64, 32, 16 blocks) as separate single-frequency simplex noises N_i(p) ∈ [−1,1], zero-centred (do not use the [0,1] remap). Frequencies are fixed constants and are never blended (§8.3).
GEN-10MUSTProvide a peak noise P(p) = (1 − |n(p)|)² with simplex n at wavelength 192 (default), giving sharp ridges in [0,1].
GEN-11MUSTBoth architectures use the same Ni and P instances.

5.7 Common height formula

H(p) = Offset(p) + Σ_{i=0..K−1} a_i(p) · N_i(p) + J(p) · P(p)

Terrain-first:  Offset, a_i, J are smooth functions of (C, E, PV)          (§7)
Biome-first:    Offset, a_i, J are weighted sums of per-biome constants      (§8)

H is clamped to [Hmin, Hmax] (defaults 40 and 250);  h_int = floor(H)
GEN-12SHOULDShow the share of clamped columns in the preview, so the user notices when splines or biome parameters push terrain into the clamp.
GEN-13MUSTHmin, Hmax are fixed settings (not data-driven), because h is a classification dimension in Terrain-first.

5.8 Terrain fill

GEN-14MUSTKeep the column layout of FillTerrain: stone below h_int − 4, under-block up to h_int − 1, top block at h_int, water up to WaterLevel (124). The three block types come from the column's surface source biome (§9.6). Climate overrides (ice) run afterwards and can be switched off (D-06).

8.2 Height from biome parameters

Per biome b:     H_b(p) = Offset_b + Σ_i a_{b,i} · N_i(p) + J_b · P(p)
Height stage:    w_b^hgt(p)  from the selected height method (§9)
Blended params:  Offset(p) = Σ_b w_b · Offset_b
                 a_i(p)    = Σ_b w_b · a_{b,i}
                 J(p)      = Σ_b w_b · J_b
Height:          H(p) = Offset(p) + Σ_i a_i(p) · N_i(p) + J(p) · P(p)   ≡   Σ_b w_b · H_b(p)
BIO-02MUSTCompute H once from blended parameters (one evaluation of Ni and P per column). Because the pipeline is linear in all biome parameters, this equals the weighted sum of per-biome heights (TST-05).
BIO-03MUSTAll biomes sample the same Ni and P; biomes differ only in their coefficients.

8.3 Design rule: blend parameters only when the pipeline is linear

Never blend frequency. Interpolating a frequency f across a transition samples the noise at x · f(x). At x = 10 000 a 1 % change of f shifts the sample position by 100 units, so the transition zone looks compressed and chaotic. Roughness is therefore expressed through octave weights on fixed-frequency octaves: a desert weights low octaves strongly and high octaves weakly, a mountain the opposite.

Any future biome parameter must enter H linearly (as a coefficient on a fixed noise). Otherwise parameter blending no longer equals height blending.

9.2 Method 1 — None

w_b(p) = 1 if b = argmin_c d_c(v(p)), else 0

9.3 Method 2 — DistanceBlend (spatial kernel, fixed width)

L = { q = (s·i, s·j) : i, j ∈ ℤ }                 world-aligned lattice, stride s
k(r) = max(0, 1 − r²/R²)²                          compact, smooth kernel, R = B/2
w_b(p) = Σ_{q∈L, |q−p|<R} k(|q−p|) · [nn(q) = b]  /  Σ_{q∈L, |q−p|<R} k(|q−p|)
nn(q) = hard classification at q (architecture's own 5D/6D vector)
BLD-10MUSTParameter: transition width B in blocks, default 32 → R = 16. Stride s = clamp(floor(R/4), 1, 2), so the lattice never causes visible squareness. B is the 0–100 % width for a straight boundary.
BLD-11MUSTIn the chunk job, compute nn(q) once per lattice point on a padded lattice (chunk bounds ± R), then convolve. The result equals the pure function (GEN-02).
BLD-12MUSTPrecompute the kernel taps (offsets and k values, fixed order) once per settings change into a NativeArray, and use the same tap list in cached and pure paths, so the summation order and float result are identical.

Rejected alternative: signed distance to the nearest boundary. It is ill-defined at junctions of three or more biomes and needs unbounded search; the kernel blend is bounded by R.

9.4 Method 3 — DistortedBoundary (domain warp)

d(q) = A · ( Ω_x(q), Ω_z(q) )                     warp field, Ω ∈ [−1,1], wavelength λ_d
nn~(q) = hard classification of v(q + d(q))      fields are sampled at the warped position
                                                  (Terrain-first: includes h(q + d(q)))

Material stage:  w_b(p) = [nn~(p) = b]                                   warp only, no mixing
Height stage:    w_b(p) = kernel blend of nn~ over the lattice (as §9.3)  warp + distance blend
BLD-20MUSTBoth stages use the same warp field Ω and the same amplitude A (DEC-05), so the material edge always lies on the height ramp. Defaults: A = 24 blocks, λd = 96 blocks, 2 octaves.
BLD-21MUSTOnly the classification position is warped. Height (Terrain-first), detail octaves and P are always sampled at the unwarped p.
BLD-22MUSTLabel in code and docs that the height-stage variant is a combination of two techniques (warp + distance blend, after Fischer et al., AutoBiomes) using the same Bhgt as method 2.

9.5 Method 4 — ParameterSpaceWeighting (soft nearest neighbour)

d_b = parameter-space distance (§6.4),  d_min = min_c d_c
w_b(p) = exp( −(d_b² − d_min²) / (2σ²) )  /  Σ_c exp( −(d_c² − d_min²) / (2σ²) )
BLD-30MUSTUse the shifted form above for numerical stability. Parameter: kernel width σ in normalised parameter units (default 0.04). 5D in Biome-first, 6D in Terrain-first.
BLD-31MUSTNo spatial neighbourhood lookups. argmaxb wb equals the hard classification (TST-07).

9.6 From weights to blocks: dithered surface pick

u = Hash01(x, z, seed, SALT_SURFACE)
S = Σ_c w_c^mat(p)
surfaceSource(p) = smallest b such that Σ_{c ≤ b} w_c^mat(p) > u · S
                  (fallback: last b with w_b > 0, guards against rounding)
BLD-40MUSTBlocks are discrete, so blending is realised by per-column random selection with white-noise hashing. No ordered (Bayer) dithering; it imprints a grid. The chosen biome supplies top, under and stone blocks for the column.

E2 · GPU culling (Phase C)

Today every render buffer is drawn in full with one DrawProceduralIndirect (bounds of 100 000 units, so Unity never culls). Culling.compute is unfinished and does not compile (F-20). The user wants it finished (DEC-13). Points live in pages of 256 inside large buffers, and every page belongs to exactly one partition, so culling works per page.

CUL-01MUSTEach RenderBuffer keeps a GPU buffer _PageBounds (min/max float3 per page, from the owning partition's AABB), written when pages are allocated and cleared when released, next to the existing _CountsPerPage.
CUL-02MUSTPer camera and frame, before drawing, a culling kernel runs one thread per page: if count > 0 and the AABB intersects the camera frustum, append the page index to _VisiblePages. A second tiny kernel (after GraphicsBuffer.CopyCount) writes the indirect args: vertex count = visiblePages × 256 × 6.
CUL-03MUSTVertex pulling uses the visible page list instead of the per-point index buffer: slot = vertexID / 6, page = _VisiblePages[slot / 256], inPage = slot % 256; if inPage ≥ _CountsPerPage[page], output a degenerate triangle (all corners at the same position) so the rasteriser drops it; otherwise the point index is page × 256 + inPage. This also removes the per-point Append loop of ReBuildIndexAndArgs. The waste is at most one partly filled page per partition.
CUL-04MUSTFrustum planes from GeometryUtility.CalculateFrustumPlanes(cam) (normals point inward; a box is outside if its positive vertex has dot(n, p) + d < 0). Culling runs per camera that renders (game, scene view, others) with its own visible-page and args buffers, created lazily per camera and released when the camera is gone.
CUL-05MUSTShadows: geometry outside the view can cast shadows into it. With shadows on, draw twice: the main pass with the view-frustum list and ShadowCastingMode.Off, and a ShadowsOnly pass with a second list whose test uses the page AABB extruded along the main light direction by the shadow distance. With shadows off, only the main pass.
CUL-06MUSTKeep a setting GpuCulling (on by default) that falls back to "all valid pages visible", for debugging and before/after comparison. Debug overlay: visible pages / total pages per buffer and layer; a "freeze culling" toggle that keeps the last frustum so you can fly out and look at what was culled.
CUL-07MUSTDelete the old Culling.compute once the new kernels work (it is replaced, F-20).
CUL-08MUSTTests: a C# reference of the AABB-frustum test (inside, outside, intersecting, behind the camera, box containing the camera) as an EditMode test; the extruded shadow test; a PlayMode test that compares the GPU visible-page set (read back) with the C# reference for 50 random camera poses; a performance comparison culling on/off at a fixed viewpoint (GPU frame time via FrameTimingManager where available).
CUL-20MAYLater (not part of Phase C): Hi-Z occlusion culling — build a depth pyramid from the previous frame's depth and test page AABBs against it, with a second pass for pages that became visible. Useful behind mountains.

E3 · Lighting (Phase L)

The data structures are prepared but unused: ChunkLightData/PartitionLightData (one byte per voxel, interval list), ChunkAccessor.GetLightInPartition, and per-corner sun and artificial light bits in the point format. PointBuilder currently writes sun 15 and artificial 0 everywhere. The user wants sky light, RGB block light and a day/night cycle (DEC-18).

E3.1 Data

LGT-01MUSTLight per voxel is 16 bits: sky(4) | R(4) | G(4) | B(4), levels 0–15. Store it chunk-wide as UnsafeIntervalList<ushort> with the same Flatten order as the voxel data (replacing the per-partition byte lists), so the GPU upload can reuse the voxel-data path. Requires F-12/F-13 fixed.
LGT-02MUSTNew voxel properties: LightEmission (RGB, 0–15 per channel; e.g. Lava (15, 9, 3)) and LightAttenuation (0–15 extra loss per step; defaults: solid 15 = opaque, water 2, leaves 1, glass 0, air 0). The existing glow stays a render effect and is independent of emission.

E3.2 Propagation

LGT-03MUSTEach channel propagates independently: L(v) = max(emission(v), max over 6 neighbours (L(n) − 1 − attenuation(v))), clamped at 0; opaque voxels hold 0. Sky light additionally travels straight down without loss through voxels with attenuation 0 (a sky column stays 15 down to the first non-clear voxel).
LGT-04MUSTInitial light of a chunk is computed by a Burst job over the region chunk ± 14 blocks in x and z (full height), reading the 3 × 3 chunks' voxel data and writing only the centre chunk's light. This is exact: light at horizontal distance d is at most 15 − d, so a source 15 blocks away contributes 0 and nothing from outside that region can reach the centre chunk (the margin was 15 until 2026-10-21), and no job writes to another chunk (no cross-chunk races). Seeds: sky columns scanned top-down; emitters. Then a BFS with NativeQueue.
LGT-05MUSTFast path for natural terrain: in the 2.5D world every air column above the surface is sky 15 without BFS. The BFS starts only from frontier voxels (a lit voxel next to a darker non-opaque voxel: under leaves, under water, at emitters). A chunk without such voxels finishes after the column scan.
LGT-06MUSTPipeline: chunk data ready → (3 × 3 data ready) → light job → (3 × 3 light ready) → meshing, because faces at chunk borders sample the neighbour's light. Add a LightScheduler in the same style as the other job schedulers and a light step in the VoxelEngineScheduler round robin. The load ring grows by one chunk accordingly; document it in ChunkPipeline.md.
LGT-07MUSTEdits: SetVoxel triggers an incremental update with the usual two-queue method (removal BFS for light that came through the changed voxel, then re-propagation from the remaining border and from new emitters/sky). Runs synchronously as a Burst job (Run(), bounded by a 15-block radius). Only after any running mesh/collider job that reads these chunks is completed (F-01). Partitions whose light changed are flagged for remesh. The result must equal a full recomputation (LGT-11).

E3.3 GPU and shading

LGT-08MUSTUpload light per chunk next to the voxel data and decompress it into the upper 16 bits of the existing per-voxel uint on the GPU (voxel id stays in the lower 16), so a neighbour lookup in PointBuilder fetches id and light at once.
LGT-09MUSTSmooth lighting in PointBuilder: per face corner, average each channel over the up to 4 voxels in front of the face that touch the corner (front voxel, two side neighbours, diagonal), skipping opaque ones. Packing in PointData.packed (all 16 bits = 4 corners × 4 bits): y = sky (bits 0–15) | R (16–31); w (currently unused) = G (0–15) | B (16–31). Update the accessors in VoxelCommon.hlsl and the comment on PointData; point size does not change.
LGT-10MUSTShading (solid, transparent, foliage shaders): light = max(skyCurve(sky) · _VoxelSkyBrightness · _VoxelSkyTint, blockCurve(RGB)), never below a small ambient; then × AO; glow as today. A DayNightCycle component drives _VoxelSkyBrightness, _VoxelSkyTint and the rotation of the URP main directional light from a configurable time of day and speed. Day/night never re-propagates light.

16.3 Collider meshing from a flat collision mask

Recorded 2026-10-21 (engine review on phase/cleanup). Measurements in the Done list.

  • Today: CMeshBuildJob reads every voxel and every face neighbour through ChunkAccessor.GetVoxelInPartition, which is a binary search in the chunk's interval list each time. 17.2 Tree species

VEG-10MUSTA new asset type TreeSpecies (ScriptableObject) describes a parametric tree kind. A FloraRule names a SpeciesVoxel, a SpeciesStructure or a SpeciesTree, exactly one of them (DEC-30). Hand-made VoxelStructure species stay supported. The Burst mirror is a flattened table in WorldGenConfig like FloraStructures, without managed types (R2).
VEG-11MUSTA species holds one or more variants, each with a weight. A variant has:
  • Trunk: voxel, height range, width 1 or 2, an optional lean of up to 1 block per 4 blocks of height, and an optional lying mode for fallen logs (§17.5).
  • Crown: shape None, Round, Ellipsoid, Cone or Tiered, a radius range, a height range, the leaf voxel, and how far the crown sits above or below the trunk top.
  • Branches: a count range, the style Diagonal (up and out, as on oaks and dead trees) or Arm (out one block, then up, as on cacti), a length range, the height band on the trunk, and an optional leaf cluster with its radius range at the tip.
  • Crown noise: the parameters of §17.3.
  • Spacing radius: replaces the global rtree for this variant (VEG-13).
VEG-12MUSTEvery value of a tree is a pure function of its anchor column and the config (R3). The variant is the weighted pick with Hash01(x, z, seed, SALT_TREE_VARIANT). Each range is rolled with its own salt from SALT_TREE_SHAPE + i. The branch directions are rolled the same way. A tree therefore comes out identical in every chunk that holds part of it, and only the clipping to the chunk differs.
VEG-13MUSTSpacing per variant. The variant is rolled before the anchor test, so every candidate's spacing radius r is known. Candidate a suppresses candidate b when their distance is at most max(r_a, r_b) and a outranks b (FloraPlacement.Outranks). This keeps a strict order, so at most one of any two conflicting candidates becomes an anchor. FloraReach becomes the largest horizontal reach of any variant (crown radius plus branch length plus lean, from the range maxima). FloraPadding becomes FloraReach + the largest spacing radius. The global TreeSpacingRadius stays the default for structure and stack species.
VEG-14MUSTStamping keeps today's rules. A flora voxel replaces only a voxel of a lower FloraVoxelClass, and anchors are stamped in world (x, then z) order. A trunk always reaches its crown, and branches start on the trunk. Trunks start at the anchor's top block + 1. A width-2 trunk and a lean are checked against the terrain heights in their footprint, and the variant falls back to width 1 without lean when that footprint is not flat within 1 block.
VEG-15MAYThe region API (GEN-17) gets an optional FloraVariant buffer next to FloraSpecies. Species ids stay stable and variants never get their own species id, so the Part III flora metrics count species, not shapes.

17.3 Crown variety

VEG-20MUSTCrowns differ voxel by voxel. For every crown voxel at world position p, a 3D hash Hash01(p, seed, SALT_CROWN) decides three things:
  • Holes: an outer-shell voxel is dropped with phole (placeholder 0.2). Interior voxels stay, so the crown never becomes see-through.
  • Bumps: with pbump (placeholder 0.1), an outer voxel gets one extra voxel outward along its outward axis. A voxel on the crown's lower edge can instead hang one block down with phang (placeholder 0.05).
  • Mix: with palt (placeholder 0), the voxel takes the variant's alternative leaf voxel instead of the main one.
Add Hash32(int x, int y, int z, uint seed, uint salt) and its Hash01 to Hash, with the same avalanche quality as the 2D hash (GEN-04). Because the decision depends on world position only, two overlapping trees agree on every shared voxel, and chunk borders stay seamless. The extra voxels count towards FloraReach.

17.4 Groves and clearings

VEG-30MUSTFlora density follows low-frequency noise instead of white noise. WorldGenSettings gets up to four density noises: Trees, Undergrowth, Flowers and Ground details. Each has its own salt, scale (placeholders 96, 48, 24 and 64 blocks) and contrast. A FloraRule names one of them and an influence k ∈ [0, 1], with a placeholder of 0 so existing rules are unchanged. The column's probability becomes p' = p · lerp(1, m(D), k), where m maps the noise D to [0, 2] with mean 1. The long-run density thus stays p, but plants cluster into groves and patches with clearings between them.
VEG-31MUSTThe cumulative intervals of a biome's rules are computed per column from p'. When their sum exceeds 1, all p' are scaled down to a sum of 1. The multi-block pre-filter (MayBeMultiBlock) must stay a necessary condition, so its intervals are built from the largest possible p' (factor 2 at k = 1). Each density noise is evaluated once per column, as PERF-07 requires for the fields.
VEG-32MUSTA switch FloraDensityNoise on WorldGenSettings (on by default) turns all density noises off. It is part of ToCanonicalJson(), so Part III runs can be made with even density and their manifests show which way they ran (EXP-10).

17.5 Ground details and beaches

VEG-40MUSTBoulders are a TreeSpecies with crown Round, no trunk and stone voxels (placeholders Stone, StoneGrey and StoneGrassy as variants, radius 1–2). The boulder sits 0–1 blocks into the ground. Crown noise applies, so boulders are not perfect spheres. They follow the anchor spacing like trees.
VEG-41MUSTFallen logs are a TreeSpecies with a lying trunk: a horizontal line of 3–6 log voxels along x or z, picked by hash, starting at the anchor. The log is placed only when the terrain height of every column under it equals the anchor's height. Those heights come from WorldSampler (pure), so all chunks agree. Otherwise the variant falls back to a log 2 blocks long, or to no log. Its reach is the maximum length. Placeholders: Forest LogOak and LogBirch, Plains LogOak.
GEN-40MUSTBeaches are patchy, not along every shore (DEC-33). Each Biome gets an optional BeachBlock (placeholder Sand, empty for Snow and Mountain) and a beach height hb,max (placeholder 3). A noise B (own salt, placeholder scale 128 blocks) gives each column a beach height h_b = round(h_b,max · s(B)), where s is 0 below a threshold (placeholder 0.45, which leaves about half of the shores without a beach) and rises smoothly to 1. A column whose top block lies 0 … hb − 1 blocks above the water surface takes the BeachBlock as its top block and its under block for 2 blocks. GEN-30 still applies below the water. Flora rules see beach columns as ground of the beach block: a rule with RequiresBeachGround grows only there and other rules skip them.
GEN-41SHOULDThe height-band test of GEN-40 can also turn low flats away from any water into sand. The agent measures how often this happens in the preview at 4096² for both architectures and reports it. If the user finds it too frequent, a water-distance test such as a distance field built on the padded lattice, becomes a follow-up decision.
